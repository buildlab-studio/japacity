# The server: the authority, its log, its limits and its tools

> Rests on `engine.md` (engine:same-inputs-same-result, engine:stale-commands-rejected, engine:view-holds-no-hidden-field, engine:seed-never-leaves-authority, engine:state-is-plain-data, engine:content-checked-before-play, engine:browser-authority-for-dev-only, engine:numbers-read-from-content), wallet:ledger-report-raises-alarms (the ledger report), `../design/04-where-things-live.md` (sections 3, 5 and 7 bind). The platform's limits are linked under Sources. The stack is in `../decisions/0006-the-online-stack.md`.
> Kinds: none of its own. The code lives in `apps/server` and `packages/store`; `packages/sim` holds two pure functions for it (see Contract).

The server is the only authority for the public game (engine:browser-authority-for-dev-only). It holds each character's seed and commands, runs the same `step` the client was built against, and answers with a view. It keeps a log it can replay, so a wrong account can be found and mended alone. Nothing a player does with the client can make a number the server did not make.

## Rules: every command through the server

**server:commands-only-through-route** A command for a character reaches `step` only through the server's command route (`POST /api/command`). The server stamps it with the current tick (clock:server-owns-the-clock) and the sender `player`, and never accepts a state, a world, a seed, a tick or a result from the client.

**server:one-command-one-transaction** One command is one database transaction, in this order: lock the character's row; reject with `stale` unless `basedOn` equals the stored version (engine:stale-commands-rejected); load the latest snapshot and replay the commands logged after it; check the hash (server:log-rows-hash-state); grant earned turns (clock:earned-turns-granted-first); `step`; append one log row per accepted command; raise the stored version; write a snapshot when server:snapshots-bound-replay says so; record the ledger mark when the day has turned (server:daily-money-report); commit. The nudge is sent after the commit, never inside it. Inside a transaction every read goes through its client; the handle's lock is never re-entered, since a command that re-entered it would wait on its own lock for ever: the work reads and writes only through the stores the transaction hands it (`TxStores`, bound to its own client: the world rows of the replay, the tickets of a purchase, the audit copy of a rollback), and a refused write rolls back what the work wrote through them. Decision 0006. A request has at most one database client of its own (decision 0006), opened when a store or the auth library sends its first statement and closed in `waitUntil` once the reply and its background work have settled; a request that reads nothing from the database (`/api/health`, a refusal before the session is read, the socket's upgrade until it asks for the character, staging's files) opens none, and a command opens exactly one, which the session, the stores and the transaction share. The switch and counter stores kept by the isolate open their own client per call, as server:four-off-switches and analytics:server-checks-every-batch say.

**server:log-rows-hash-state** Each log row holds the command, its tick, its sender, the version after it and `hashState` of the state after it. Every load replays from the snapshot and compares the result's hash with the last row's; on a mismatch that account alone is refused with `diverged` and queued for the rollback tool (server:rollback-check-finds-divergence), and every other account carries on.

**server:snapshots-bound-replay** A snapshot of the full state is written when a segment begins and whenever the version reaches a multiple of `server.snapshotEvery`; a load never replays more than that many commands.

**server:rejections-write-nothing** A rejected command writes nothing, logs nothing and raises nothing, as engine:only-events-change-state asks of the simulation. The server counts rejections by code for the admin page only.

**server:authority-commands-same-path** An authority command (any of `AUTHORITY_COMMANDS`, server:apologies-never-currency) goes through the same transaction as a player's, with the sender `authority`, and is logged the same way. An authority command for a character whose row is locked waits for the lock.

**server:paired-rows-locked-in-order** A change that touches two characters locks both rows in ascending id order before reading either (`../design/04-where-things-live.md` section 7). The store interface supports it, so pairs need no locking of their own.

## Rules: the rollback tool

**server:rollback-check-finds-divergence** `rollback check <account>` replays that account from the base of its first segment, against the stored world rows (clock:command-uses-stamped-tick) and the content each segment names, and reports the first logged version whose hash differs, or that none does. It reads only; it locks no other account.

**server:rollback-apply-one-account** `rollback apply <account>` corrects that account only. Under the account's row lock it replays as the check does; a command the log says was accepted and that is now rejected is dropped and listed; the replayed state becomes the base of a new segment at the next version; the old segment's rows are kept in the audit table. The client's next command is `stale` and it refetches.

**server:no-mass-rollback** There is no command that freezes, rolls back or corrects more than one account. A fault that touches many accounts is mended by running the tool once per account, each in its own transaction, while every other account plays on. The one exception is `pnpm snapshot:all` (server:snapshot-before-deploy), which walks every character a page at a time and gives each its own transaction; the admin-source test names it.

## Rules: money

**server:daily-money-report** The money report: once a day, at 00:00 UTC, a job takes every account that logged a command that day, subtracts the ledger totals stored at its last mark from its totals now, adds the difference to the day's totals by reason and currency, and stores the new mark. The day's report lists money created and destroyed by reason, by currency, by day, leaving out the transfers `convert`, `move` and `remit` as `ledgerReport` does. The day's totals are added and the mark is moved in one transaction through the ledger store, at the job and after a day's first commit alike, with the mark read again inside it (as decision 0006 hands a transaction its stores), so a failure between the two writes keeps neither and a rerun adds the day once. The admin page's Money tab asks for yesterday's report, or a UTC day typed as `2026-10-07`, and a typed day that is no day of the calendar (`2026-02-30`, `2026-04-31`, `2026-13-01`) cannot be sent.

**server:ledger-alarm-lists-suspects** The alarm: the same job runs `ledgerReport` (wallet:ledger-report-raises-alarms) on each of those accounts, and lists every account it names as suspect, with the reason, currency, total and ceiling, on the admin page. A draw whose `win` payments exceed its prize fund raises a world alarm (lottery:money-report-checks-draws). An alarm takes no action by itself: a person looks, then uses server:rollback-apply-one-account on that account if it is wrong. The admin page is open only to the accounts in the deployment's Worker secret `ADMIN_ACCOUNTS` (comma-separated account ids, each trimmed); unset or empty, it is open to nobody. It is set once per environment with `wrangler secret put ADMIN_ACCOUNTS` (`--env staging` for staging) and named neither in `wrangler.jsonc` nor on a deploy's command line, so no account id is written in a committed file or shown as a plain variable, a deploy keeps it as set, and a fork starts with no admin. It is a secret and not a variable, since a variable shows its value in the dashboard, and a variable and a secret may not share a name. So that the admin's reads never slow the players' database, every admin read (a GET under `/api/admin/`: the money report, the alarms, the rollback check, the analytics and the numbers, the moderation, adverts and switches pages) runs each store call as a transaction of its own that begins with `SET LOCAL statement_timeout` (5 seconds), so no statement of a heavy report runs longer and the game is never slowed by one. `SET LOCAL` is the form that is safe through Hyperdrive: it pools in transaction mode, holds one connection for a transaction to its end and resets a connection before another client takes it, so the setting ends with its transaction and never reaches a player's statement, where a session `SET` would last one statement or leak. A read stopped by the timeout (SQLSTATE 57014) is answered to the admin as a refusal, 503 with `not-possible` and words that say why, not as the server's failure; on a game route the same code stays server:no-platform-error-page's `unavailable`. The admin's writes are single rows and run without that timeout.

**server:apologies-never-currency** Never give currency as an apology. When players are owed for an outage or a fault, the server gives turns through `turns/grant` or a cosmetic item, never money of any currency. The authority commands are the closed list `AUTHORITY_COMMANDS` (`packages/sim/src/engine/step.ts`, decision 0005): `turns/grant`, `lottery/pay`, `wallet/top-up`, the people commands of `person.md` (`people/link`, `people/facts`, `people/moments`, `people/proposal`, `people/agreed`, `people/ended`, `people/declined`, `people/withdrawn`, `people/gossip`, `people/stand-in`, `people/family-request`), the interview's `interview/open` and `interview/scored`, and `home/host` (the host learns of a guest; it raises the host's own upkeep and credits nothing). Only `lottery/pay` and `wallet/top-up` credit money: `lottery/pay` only from a draw's prize fund, and `wallet/top-up` only naira bought with real money, marked (wallet:top-ups-are-marked); no server route sends `wallet/top-up`. A test lists every command the simulation accepts from the authority and proves no other one credits a pocket.

**server:overlays-never-multiply-prices** Never fix prices by multiplying them. An overlay names each value it changes; it has no factor field. `checkOverlay(base, overlay)` refuses an overlay that raises any cost or fee that a new character can meet: the entries whose requirements hold for some scenario's starting state, judged with `check` on that state. Drains go on what only established characters buy, and new players are left alone.

## Rules: public rules, private dials

**server:secrets-stay-on-server** These stay on the server and never reach a reply, a socket, a log line the client can read or the client bundle: every character seed, the world seed, the stream draw counts, the director's book, any world tick after the current one, a result not yet announced to the player (whether an offer is a fraud, a decision not yet due, a draw's secret before it is revealed), the overlay's values and the alarm ceilings. A reply carries only the view, the report lines, the current world and the clock.

**server:hidden-values-made-once** Hidden values are made once. A character's seed is 128 bits from `crypto.getRandomValues` when the character is created; the world seed is made the same way once, at the first deploy, and kept as a secret of the deployment; an overlay is applied once when the server starts (`applyOverlay`) and the result kept for the life of the isolate. None is ever made again from the request.

**server:build-scanned-for-secrets** A test builds the production client with a test overlay that holds sentinel values, a test world seed and a test character seed, then scans every file of the build output and fails if any of the three appears. It also fails if the bundle contains any module of `apps/server`, `packages/store` or `packages/db`.

**server:public-defaults-run-the-game** The public defaults alone run the whole game and pass every test (engine:numbers-read-from-content). A private overlay may change the live numbers; it never changes a rule.

**server:client-never-predicts** The client does not predict results: it shows the command as sent until the reply arrives. The client holds a view, not a state, and almost every turn draws on a hidden stream, so a prediction would be wrong too often to be worth the code. The round trip from Lagos to London is about 100 ms each way.

## Rules: versions and old saves

**server:save-is-list-of-segments** A save is a list of segments. Each segment names its content version and overlay version, and starts from either the scenario and seed (the first) or a base state (each later one); its commands follow. Replay runs each segment under the content it names.

**server:newer-content-upgrades-state** When a character is loaded under content newer than its last segment's, the server replays the segment under its own content, applies `upgradeState(state, from, to)`, checks the result with every kind's invariants and `checkContent`, and opens a new segment with that state as its base, in one transaction.

**server:upgrade-state-is-pure** `upgradeState` is pure: it renames ids through the content's rename table, builds any slice the state lacks with that kind's `initial` (decision 0001, point 3), and raises `schema` where the shape changed. A test upgrades the end state of every golden life from an older content (a stand-in with older ids) to the current and checks the invariants. `grownTo4` in `upgradeStateWith` raises a state of schema 3 or below to 4: it fills the fields that grew inside a slice (the month's `turn.spent`, `offer.rolled` and `offer.rolledMonth`, the body's `quality.belly` and `quality.energy`) with their kind's starting values and keeps every value the state holds, and a state with no `things` slice gets it built by its kind's `initial` (home:things-a-life-owns); the invariants are not loosened. A test upgrades every golden life from the schema 3 shape under a stand-in older content to the current.

**server:older-contents-bundled** The server bundles the current content and every older content version a life may still name. The older versions are `olderContents`, beside `version` in `packages/content/src/index.ts`, each kept exactly as it shipped. `withContentBefore` (`authority/overlay.ts`) adds them to the worker's `Contents.older`, and under an overlay each a second time with the overlay applied when it fits, so a segment saved under one is found and upgraded on its first load (server:newer-content-upgrades-state); the lookups in the dials and the money job read the same list. Content version 1 is the first, and the list holds every version below the current one, each frozen as it shipped (server:older-content-frozen): that version's content as it shipped, which is the current data under the old version's name when only the simulation's code changed (server:content-version-sealed says when a version is raised). A segment that names a version not bundled cannot be loaded and has nothing written, and the snapshot tool lists its character as failed (server:snapshot-before-deploy). A character still on an older content is carried to the current one when it is next loaded, in that load's transaction: a command, the view's fetch, a pair's invite or the snapshot tool when it opens a new segment for it (server:snapshot-before-deploy). The upgrade is written only when that transaction writes; a rejected command writes neither (server:rejections-write-nothing). Nothing upgrades a character that is not loaded. An older content can leave the list only when no character's segment in force names it, since a segment under a content the server does not bundle cannot be loaded. A life whose commands since its last snapshot replay differently under the current simulation is refused as diverged before the upgrade runs (server:log-rows-hash-state); at a staging deploy such lives start again. A test plays typical lives through the server's own routes under each version in `olderContents` and under a stand-in older version, then loads and plays each under the current content: none diverges or is rejected, the upgrade is written once, and the carried state passes the invariants (`apps/server/src/authority/carry.test.ts`). A deploy is rolled back only to a commit that bundles every content version a life's segment names, since a life carried to a newer version cannot be loaded by code that does not bundle it.

**server:overlay-change-opens-segment** An overlay change is a content change for this purpose: a segment records the overlay it ran under (engine:state-is-plain-data), and a new overlay opens a new segment at the character's next load.

**server:content-version-sealed** The content version moves with what a replay depends on. A content version is a whole number from 1, written as a string (`version` in `packages/content/src/index.ts`). Beside it, `packages/content/src/seal.json` holds the version and a fingerprint: SHA-256 over the content object serialized with its keys in the order the content has them (its version aside; the simulation meets a table's entries in that order, so a reorder alone moves the fingerprint) and over every file of the simulation's source (`packages/sim/src`, without its tests, its test helpers and the `simulated-play`, `testing` and `goldens` folders), each printed by the TypeScript printer with comments removed and kept as its tokens. A comment, a change of layout or a test leaves the fingerprint as it was; a changed number in content, a changed line of the simulation's code or a file added to it moves it. `pnpm check:version` (`tools/check/version.ts`, a step of `pnpm check` and of the check workflow) fails when the fingerprint moved and the version did not, and says what to do: raise the version by one, add the content of the old version to `olderContents` as it shipped when lives exist under it (server:older-contents-bundled), and seal. It also fails while the seal names a version other than the content's. `pnpm content:seal` writes the seal and refuses a changed fingerprint under the version already sealed; a version that is not a whole number from 1, or is below the sealed one, is refused by both.

**server:older-content-frozen** `pnpm content:freeze` keeps the shipped content before a version is raised: it writes the sealed version's content, exactly as the server bundles it, to `packages/content/src/older/<version>`, with the fingerprint of that content alone, and lists it in `olderContents`. It refuses while the content's fingerprint differs from the seal (only what shipped is frozen) and when that version is already frozen. Every version below the current one is frozen and listed, whether or not lives were found under it, since no check can see the databases. `pnpm check:version` fails when a version below the current one is not frozen or not listed, when a frozen version's content no longer matches its fingerprint (nobody edits a frozen version), and when a frozen version is at or above the current one. A frozen version reaches the server's bundle and never the client's first visit (engine:first-download-has-budget).

## Rules: rate limits

**server:per-account-rate-limits** Each account may send at most `limits.commandsPer10s` commands in 10 seconds and `limits.commandsPer60s` in 60 seconds, and fetch the view at most `limits.readsPer60s` times in 60 seconds. Over a limit the request is answered `429` with the code `rate-limited` and a `retryAfter` in seconds; the command is not stepped and nothing is logged. The command limits also count the account's change and deletion, the age screen's answer, feedback and an appeal; the read limit also counts reading the account and the age screen, a place's people, opening the presence socket and the standing. The anonymous sign-in counts as a command for server:per-account-rate-limits and is refused `too-many` by account:guest-floods-are-capped before it. The client keeps under the command limit on its own: every request on it leaves the remote authority at most eight in any ten seconds, two under `limits.commandsPer10s`, and the next waits for room rather than be refused. The prologue's preset is not sent step by step: Begin sends it as one request to `POST /api/prologue/preset` (server:server-plays-prologue-preset, decision 0008), which counts once against the limit.

**server:anonymous-limit-by-address** A request with no session is limited by address: `limits.anonPer60s` in 60 seconds, keyed on the `cf-connecting-ip` header. Every limit the server keeps by address (this one, the lights, the content policy reports, the counters and the account routes' own) keys an IPv4 address whole and an IPv6 address by its first 64 bits, since one phone or home holds a whole /64 and could step round a limit keyed on the full address.

**server:noisy-socket-closed** A socket that sends more than `limits.socketPer10s` messages in 10 seconds is closed with code 1008 and may reconnect after the wait in clock:sockets-reconnect-with-backoff. A ping answered by the automatic reply (clock:client-sends-only-pings) never wakes the place's object and is not counted; every other message is.

**server:limits-are-approximate** The limits use Cloudflare's rate-limit binding, which counts per location and is eventually consistent. That is enough for abuse control. The limits are not an accounting system, and nothing in the game depends on a count being exact.

**server:spending-alerts** The bill has no cap, so the deployment carries spending alerts: a warning at $50 and $200 in a month, levels the operator may change.

## Rules: dials, switches and one crowd

While players are few, these rules keep a small crowd together and let it be steered without a deploy. The rules are public; the numbers are the operator's to set.

**server:private-settings-and-dials** The private settings are the private overlay (server:public-defaults-run-the-game) plus the switch row of server:four-off-switches, both server-only (server:secrets-stay-on-server). Two dials live in the overlay: the target headcount of each place (city:residents-fill-to-target, each entry's `crowd.target`) and how readily a computer partner is offered (person:computer-partner-offer-dial, `tuning.people.computerAfterMonths`). The lottery's odds (lottery:odds-fixed-at-draw-open, `tuning.lottery.odds`) live there too. The public content holds working values for all three, and the public defaults run the whole game.

**server:four-off-switches** Four off switches live in one switch row in the database: `signups`, `lottery`, `adverts` and `partnerPlay`, each on by default. The server reads the row on each request, cached for at most `switches.cacheMs`, so a switch takes effect without a deploy; every change is written to the admin log (moderation:admin-actions-logged-append-only) with who and why. Off, each does only this:
- `signups`: creating an account is refused with `switched-off` and the visitor sees server:signups-off-shows-full's screen; accounts that exist sign in and play as usual.
- `lottery`: `lottery/buy` is refused with `switched-off` before it reaches `step`, and the lottery screen says sales are paused; a draw already on sale still closes, draws and pays what was sold.
- `adverts`: no campaign is served (advert:campaign-chosen-without-player-data), and no slot renders an advert.
- `partnerPlay`: invite cards cannot be made or opened, and no new pair record is made between players; pairs that exist carry on, and computer characters fill every slot as `person.md` allows.

**server:signups-off-shows-full** While `signups` is off, a new visitor sees one screen, the text key `server.full` ("Japacity is full right now. Try again shortly."), with no sign-in form and a button that checks again after `switches.retryMs`. A signed-in player never sees it.

**server:one-shared-world** There is one copy of each place and one lottery for everyone: no copy of the world per country, no modes, no separate servers by country. The only split is clock:busy-place-splits-rooms's numbered rooms, which open only when a place passes its socket cap. A small crowd split in two looks empty twice.

## Rules: guards on every request

**server:security-headers-on-replies** Every reply carries the security headers (`security/headers.ts`): a content policy, nosniff, no framing, no referrer, `no-store` unless the route sets its own caching. The socket upgrade is left alone.

**server:same-origin-writes-only** A write under `/api/` is refused 403 unless its origin is SITE_URL's; no origin with a cross-site fetch is refused too; `/api/auth/` is the auth library's to check.

**server:body-size-limits** A body over 64 KiB is refused 413; admin routes allow 1 MiB; `/api/counters` still answers 204.

**server:command-size-limit** A command over 4 KiB of JSON is refused before it is read.

## Rules: the environments

**server:production-and-staging** Two deployments run from `apps/server/wrangler.jsonc`: production (`japacity-server` at `japacity.app`) and staging (`japacity-server-staging` at `staging.japacity.app`, `--env staging`), each with its own Worker, database, secrets and passkeys; neither has a workers.dev address or preview URLs, and staging's block says so itself. Staging deploys through `.github/workflows/deploy-staging.yml` from a green check on `main`, the commit the check passed. Production deploys through `deploy-production.yml` from a `v*` tag, or when started by hand from `main`, after the maintainer approves the run in the `production` environment, and only the commit staging serves: the job stops first unless the commit is an ancestor of `origin/main` and equals the commit in staging's `japacity-build` meta, read at the environment's `STAGING_URL` through staging's Access service token. Each deploy ends by checking that the root answers 200, `/api/health` answers ok and the page's meta carries the commit deployed, asking up to six times, five seconds apart (staging's through the Access service token), and fails when they never all hold. A deploy by hand from a checkout, in the same order and with the same checks (`apps/server/README.md`), is the fallback. Staging sets `NOINDEX` and `TICK_CRON`, which production never has. `TICK_CRON` is the tick cron, thirty minutes, so the database can sleep between runs (clock:cron-stores-missing-ticks): the jobs that run on the five-minute cron run on that cron instead, and the daily jobs stay at 00:00 UTC. Production's first cron is the five-minute one. `NOINDEX` keeps staging out of search engines: there the Worker runs first for every path and serves the client's files itself through its `ASSETS` binding, every reply carries `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet`, `/robots.txt` disallows every crawler from the whole site, and a page or a file never opens a database client. Production lets the platform serve its files first and sends no such header. Both send the same files, compressed by the edge. A third way to run it, on one machine and with no paid service, deploys nothing. `pnpm dev:full` starts Postgres 18 and Mailpit in Docker Compose, applies the migrations, builds the client with Vite (watching) and runs `wrangler dev` on the top-level config, with no `--env`, serving that build and `/api` on one https origin, `https://localhost:8787`, as one Worker serves a deployment. Its values come from `.env.example` and the git-ignored `.env.local`, are checked to be on this machine, and reach wrangler only on its command line and in a git-ignored file: never in `wrangler.jsonc`. Hyperdrive's two bindings get the local string, the bot check uses Cloudflare's always-pass test keys, whose passes account:bot-check-on-guest-creation takes on a local SITE_URL only, the mail goes to Mailpit (account:sign-in-routes-rate-limited), and the five-minute cron is run by the command through wrangler's local explorer, since wrangler runs no cron locally. `pnpm test:browser:real` plays the game against it in a browser; neither is part of `pnpm check`. The shell is never stale. The client's `_headers` serves `/`, `/index.html` and every other path with `Cache-Control: no-cache` (kept, always asked about again), the content-hashed files under `/assets/` with `public, max-age=31536000, immutable`, and `/assets/manifest.json`, the one fixed name there, with `no-cache` again; on staging the Worker's `ASSETS` binding carries these headers (checked with a local `wrangler dev --env staging`). Neither deployment has a fallback page (`not_found_handling: "none"`): production names only `/api/*` for the Worker to run first, so the platform serves every file that exists from the location nearest the player and a navigation to `/api/*` (a sign-in callback) still reaches the Worker, and only a request that matches no file reaches it besides; there, as on staging, a missing file under `/assets/` is answered `404` with `no-store` and the security headers, never the page under a year's caching, and any other address gets the page (`security/files.ts`). The notice's service worker keeps no cache and answers no fetch. Every build puts its commit in `index.html` (`<meta name="japacity-build">`, marked `+changes` when the tree had uncommitted changes) and the page says it once in the console. Both environments keep Workers Logs, traces and Issues through the top-level `observability` block of server:shared-observability-block; staging has no block of its own and inherits it, as wrangler's environments inherit `observability`, so a tester's failure can be read from the server's side. Against staging an automated browser gets as far as Begin and no further: the managed bot check refuses it (account:bot-check-on-guest-creation), so the real tests stop there and skip the life's later tests, and the play driver ends its run there, none of it a failure; the whole life is played automatically on the local stack, where the test key passes, and on staging by a person.

**server:unknown-address-becomes-root** Every address that is not one of the client's files opens the game (the Worker answers it with the page through its `ASSETS` binding, server:production-and-staging), but a missing file under `/assets/`, which gets a 404. The game knows `/`, `/admin` for an account the admin view opens or asks a passkey of (moderation:admin-view-for-admin-list), and the invite address (pair:invite-link-single-use), which keeps its own page and is replaced when it closes. Once the game has settled, any other address, `/admin` for anyone else among them, is replaced by `/` in the address bar with `history.replaceState`, keeping its query and fragment, with no reload, so no player plays under an address the game does not know.

## Rules: the server's cache and its place

**server:public-replies-cached** The public replies that are the same for everyone are kept in the server's cache, Cloudflare's Cache API (`caches.default`), and read from it before the database (`apps/server/src/routes/cache.ts`). That cache is local to the data centre where the Worker runs, London with placement (server:worker-placed-near-database), so a hit saves the database query and not the player's trip to the server. The world (`GET /api/world`) is keyed by the tick and kept until the next tick (clock:world-fetch-is-jittered). A draw's page (`GET /api/draw/:n`) is keyed by the draw's number and kept 60 seconds while it is not drawn and a day once it is (lottery:fingerprint-commits-secret, lottery:ticket-list-frozen-anonymously, lottery:result-published-in-tick-row). The advert slots (`GET /api/adverts`) are keyed by the region the server settles on and the hour, and an approved advert image by its creative, its version and the hour (advert:campaign-chosen-without-player-data); the browser keeps each until the hour ends, the server's cache for at most five minutes (300 seconds, or until the hour ends if that is sooner). A key is a URL of the game's own origin under `/api/cache/`, with a shape number raised whenever a kept reply changes shape, since the cache outlives a deploy; nothing of the request's path, query, cookies, headers or account enters it. The rate limit is counted first (server:per-account-rate-limits), and the `adverts` switch is read before the cache (server:four-off-switches), so a refusal or a closed switch never reaches it. A missing draw or image is never kept, and nothing kept carries a cookie. A kept reply carries the moment it stops being fresh for the browser and the moment the server's cache lets it go: asked for at or after the sooner one it is made again, and a hit is sent with `public, max-age` of the browser's seconds left, so no browser is told to keep a reply longer than the first reply said. The cache is one data centre's and is not copied to others, so the database is read once per key in each location the Worker runs in. A cache that fails or is missing is a miss: the reply is made from the database. It is missing in Node and the browser tests, and the Cache API is not available to a Worker behind Cloudflare Access, which covers staging: there every public read goes to the database. The advert replies stay in the server's cache at most five minutes (advert:reported-advert-pulled-at-once), so a campaign pulled leaves new visitors' screens within five minutes, and the `adverts` switch stops every advert within its own cache of 30 seconds. The two lights (`GET /api/lights`, account:two-lights-and-wink-lines) are keyed by the hour and kept, in the cache and by the browser alike, until the hour ends. A kept reply may be cleared before its hour or window ends (`forgetKept`, and an optional `delete` on `EdgeCache`, the Cache API's own); only the dedication's shared part uses it, and the clearing reaches only the data centre that serves the request, so another may serve a copy until its window ends (five minutes for the dedication).

**server:worker-placed-near-database** Both deployments run the Worker's fetch handler near their database rather than near the player: `placement` is `{ "region": "aws:eu-west-2" }`, Neon's London region (`../design/04-where-things-live.md` sections 5 and 6), at the top level of `apps/server/wrangler.jsonc` and again in staging's block. A command makes several queries in a row (server:one-command-one-transaction), each a round trip, so each becomes short and the reply crosses from London once. Placement moves only the default fetch handler: the scheduled jobs run where they ran. Production's static files are served from the location nearest the player; on staging, where the Worker runs first for every path (server:production-and-staging), they come through the Worker. So with placement staging's files come from London and its page-load numbers do not stand for production's, where the platform serves files from the nearest location; only `/api` timings compare. The world's kept reply (server:public-replies-cached) is kept where the Worker runs, so mostly in one place. The effect is measured on staging by the time of `GET /api/world` with the Access service token, before and after a deploy that changes placement.

## Rules: the page's policy reports

**server:csp-reports-to-own-origin** The page carries two content policies in `apps/client/public/_headers`. `Content-Security-Policy` is enforced: `default-src 'self'`; scripts from `'self'`, `'wasm-unsafe-eval'` (the picture decoders), `https://challenges.cloudflare.com`, `https://static.cloudflareinsights.com` and the sha256 hash of the page's one inline script, the life's hint (world:lazy-part-fails-softly), which the build writes into both policies in place of `{inline-script-hashes}`, never `'unsafe-inline'` or `'unsafe-eval'`; frames from the bot check alone; connections to `'self'`, `blob:` and `https://cloudflareinsights.com`; images `'self' data: blob:`; media and workers `'self' blob:`; fonts `'self' data:`; styles `'self' 'unsafe-inline'`; `object-src`, `base-uri`, `form-action` and `frame-ancestors` all `'none'`. `Content-Security-Policy-Report-Only` is the same policy with `require-trusted-types-for 'script'`, `trusted-types japacity`, `style-src 'self'` plus the hash of every inline style the build writes, and `style-src-attr 'none'`. The two outside scripts are named by host, not by hash or nonce: neither has a versioned address, and the page is static files with no server to mint a nonce. The build stops when the built pages' inline scripts and the hashes in the built `_headers` disagree: any inline script but the hint, on any page, a hint whose hash either policy lacks, a hash no script has, or the token left unwritten. Both policies report to `POST /api/csp-report` on the page's own origin: `report-to csp` with `Reporting-Endpoints: csp="/api/csp-report"`, and `report-uri /api/csp-report` for a browser without the Reporting API. The route (`routes/csp.ts`) counts every request against the address limit (`ANON_60S`, server:anonymous-limit-by-address) and reads no session; it accepts only `application/csp-report` and `application/reports+json` (else 415), refuses a body over 16 KiB (413) and one that is not a report of its type (400), and answers 204 with no body. Each violation, at most 20 in one request, writes one log line, `{"event":"csp-report","directive":...,"blocked":...,"path":...}`: the effective directive from a fixed list (else `other`), the blocked address's origin alone (or its scheme, or the browser's word such as `inline`), and the document's path with no host, query or fragment (an invite link's code written `:code`). Nothing else of the report is kept or logged: never the user agent, the full address, the referrer, the sample or the policy (server:secrets-stay-on-server, analytics:store-holds-nothing-personal). Each violation also adds one to the counter `client/csp`, keyed by its directive, under the request's region: a count and nothing more, as analytics:admin-stats-for-admins-only's numbers are; and one to `client/csp-blocked`, keyed `<disposition>:<directive>:<kind>`: the disposition `enforce` or `report` as the report says, else `other`; the kind from `CSP_BLOCKED_KINDS` in content: the browser's word (`inline`, `eval`, `wasm-eval`, `trusted-types-policy`, `trusted-types-sink`, `data`, `blob`), `extension` for a browser extension's scheme, `self` for the page's own origin, a host the policy names (https on the default port only), `other-host` for any other web address, and `other` for anything else; never an address. Rolling back is one rename, `Content-Security-Policy` to `Content-Security-Policy-Report-Only`, and promoting the stricter policy is the reverse.

**server:csp-holds-every-page** Every page the game serves loads under both policies without one refusal. The browser suite and the screen catalog can run against a build served by `vite preview` with the shipped `_headers` (`E2E_BUILD=development` for specs that drive the dev hooks, `production` for the build players get), and every test fails on any `securitypolicyviolation` event or policy console line (`e2e/support/policy.ts`). A violation is fixed at its cause, never by widening a policy without the reason beside it in `_headers`. The client keeps to the policies: Zod is set `jitless` before any shape is built (`public/zod-jitless.js`, deferred ahead of the entry), since its check for `Function` is itself a refused eval; a script loaded from code takes its address from the page's one Trusted Types policy, `japacity`, which passes only `https://challenges.cloudflare.com`; a built page carries no style attribute, and the build writes each inline style's hash into `_headers`, and the hash of the page's one inline script, the life's hint, into both policies.

## Rules: failures and logs

**server:shared-observability-block** Every Worker deploys with the same top-level `observability` block in its `wrangler.jsonc` (the game's, which staging inherits): `enabled`, `logs` with `head_sampling_rate: 1` and `invocation_logs` off, `traces` off, and `issues`. Cloudflare's own invocation logs and traces are off: they would record the address with its codes, the client's IP and place, and the cookie header. The server writes one log line per failure, one per policy report (server:csp-reports-to-own-origin), and nothing else: a failed request, a scheduled job that failed, an error of the auth library, a client that would not close. The line is `console.error(JSON.stringify(...))` from `apps/server/src/log.ts`, the only file of the Worker that writes to the console (tests and the Node command lines `*.main.ts` aside), with these fields only: `level`; `what`; the job's name; the method; the path's shape, every segment that is not a route word or a content id replaced by `:id` and never the query string; the status answered; the error's name, the first line of its message with emails, addresses, long ids or tokens and quoted values taken out, cut to 200 characters; its cause's name; and a SQLSTATE or socket code. It never carries a header, a cookie, a body, a session, an account id, an address or a secret (server:secrets-stay-on-server), and the auth library's own printing goes through it. The server has no build stamp, so the line has none.

**server:no-platform-error-page** No failure reaches the platform's error page. A route that throws is answered by `app.onError`, and anything that escapes the app (before or outside it, the database client and the auth library's set-up included) by a catch around the whole of `fetch`; each answers JSON `{ ok: false, code: "unavailable", detail }` with the security headers of server:security-headers-on-replies and `no-store`, and logs one line (server:shared-observability-block). The status is 503 with `Retry-After: 5` and `retryAfter: 5` when the database or an upstream did not answer: the request's own connection was refused or dropped, a socket code, pg's words for a cut connection, or a SQLSTATE of class 08, 40, 53, 57 or 58; it is 500, with no wait, for anything else, a Postgres error about the statement itself included; outside the app it is always 503. `unavailable` is not one of the game's refusals: the client shows its trouble card for it (engine:browser-authority-for-dev-only). Each scheduled job runs on its own: its rejection is caught and logged with its name, so one never stops or hides another, and once all have settled a last rejection naming the failed jobs keeps the cron's own record failed.

**server:text-the-database-can-store** Text holding U+0000 or a lone UTF-16 surrogate is refused before any query: in a body with 400 `not-legal`, as an id in the path with 404 `unknown-id`, so it never reaches the database as a failure line. A command keeps only its type's own keys.

**server:switch-log-insert-only** The switch log is insert only at the database, as the admin log is: a trigger refuses every change and removal.

## Rules: migrations and the deploy

**server:migration-before-deploy** Every deploy of the game's Worker is preceded by its migration. Each deploy workflow installs (production once its guard of server:production-and-staging has passed), then runs `pnpm --filter @japacity/db db:migrate` with the environment's `DATABASE_URL_UNPOOLED` secret, the branch's direct string for the migrator role that owns the schema and drizzle's journal (never the app role's, which cannot write them), then snapshots every character from the live commit (server:snapshot-before-deploy), then builds the client, then deploys, then checks the deployment (server:production-and-staging); the snapshot, the build and the deploy run only after the migration succeeded. Once the environment's Cloudflare pair is set, a missing `DATABASE_URL_UNPOOLED` is an error and nothing is snapshotted, built or deployed; with no Cloudflare pair the job still stops quietly at its first step. A deploy by hand keeps the same order (`apps/server/README.md`). Since the Worker still running serves requests against the migrated schema until the new one is up, a migration is additive and safe beside it: expand first, and a column or table is removed only in a later migration, once no deployed Worker reads it. The migrations start from one file, `packages/db/migrations/0000_japacity.sql`: every table in full, generated from the Drizzle schema, and at its end the insert-only functions and triggers of the admin log and the switch log, written by hand. `packages/db/src/migrations.test.ts` proves the committed migrations build the structure a fresh generate of the schema builds, apart from those hand-written functions and triggers, and that the triggers refuse an update and a delete. Migrations are incremental: a new one is generated after the last, a committed one is never edited, and with players on a database every migration only adds.

**server:snapshot-before-deploy** Every character snapshotted before a deploy, since a deploy that changes the rules would otherwise make old commands replay to another hash. `pnpm snapshot:all` runs against the database on `DATABASE_URL_UNPOOLED` (the migrator's string, as the migration step uses), one character per transaction under its row lock (server:no-mass-rollback): it loads the character as a command would (the snapshot, the replay of the logged commands under the content each segment names, the hash checked; a character that diverges is skipped, listed and left for the rollback tool), then opens a new segment at the next version with that state as its base and an empty tail, writing its snapshot (server:snapshots-bound-replay, server:save-is-list-of-segments), so the rules deployed next never replay commands logged under the rules before; a content upgrade still goes through server:newer-content-upgrades-state on the next load. It prints each character's id, versions and outcome and ends non-zero when any was skipped. The deploy workflows (`.github/workflows/deploy-staging.yml`, `deploy-production.yml`) run it on every deploy, after the migration and before the client is built and the Worker deployed: each reads the commit the environment is running from its page's `japacity-build` meta (staging's through its Access service token), checks that commit out in a worktree of the whole history, installs it with a frozen lockfile and runs `pnpm snapshot:all` on the environment's `DATABASE_URL_UNPOOLED`. A live commit that cannot be read stops the deploy, and so does a character the tool skipped; a live commit with no `snapshot:all` has nothing to run, and the step says so in a notice and goes on. A deploy by hand runs it the same way, at the same point. The tool loads each character under the rules that wrote it, so it runs from a checkout of the commit the environment is running, never from the commit about to be deployed; a database with no character needs no run. With server:rollback-check-finds-divergence and server:rollback-apply-one-account, `pnpm rollback check|apply <character>` also runs against the database on the same string through packages/db, one character per run; the `--memory` form is for a save in a file. A raise is rehearsed before its deploy on the local stack: lives kept by the play driver (`--keep`), the snapshot step run from the commit before the raise, then each life resumed under the raise (`--resume`) and checked with `pnpm rollback check`.

**server:server-plays-prologue-preset** The prologue's preset played by the server (decision 0008). `POST /api/prologue/preset` takes `{ archetype, age, home, basedOn }` (the archetype's id from content's table, the age and the home chosen at the door, the version seen) and, in one transaction as server:one-command-one-transaction runs a command (the lock, `stale` unless `basedOn` is the stored version, the load and replay, the hash check, the turns granted), steps `prologue/choose` for each step of the prologue in turn with the answer content's `presetAnswer(archetype, age, home, step, answers)` gives (the preset's answer where allowed, else the open answer that suits the archetype), one log row per accepted command, until the prologue closes or an answer is refused, at most `limits.presetSteps` steps (twenty). The version rises by the count stepped, plus an earned turn when real time has earned one. A refusal ends the batch with the steps before it committed and the refusal in the reply; refused at its first step, the preset writes nothing and answers the refusal with the clock, as a command does. The reply carries the view after the last step, the clock, the count stepped, the steps' lines, on which the handover opens, and the trail (each step with its answer, the draw once made and the outcome its draw gave) for the page (prologue:printed-page-hands-over). The request counts once against server:per-account-rate-limits's command limit; a character past its prologue, an unknown archetype, or an age or home the door does not offer is refused `not-legal`, and the client reduces a stale draft (an age past the door's range, a home the tile is not offered) to what the door offers before it is sent. The nudge is sent once after the commit. The request keeps a guest's last play (account:idle-guests-cleaned-by-hand) and its refusals are counted (analytics:nightly-game-counters).

**server:dedication-routes** The dedication routes (account:dedication-page-and-its-doors and account:name-a-light-for-yours). `GET /api/dedication/lights` answers `{ count, lights, mine }`: `count` the whole number of lights; `lights` at most 240 of `{ id, name?, years? }`, an opaque per-light id that is never the account id, the name present only when approved and the years only when it is approved and has at least one year, the approved named ones first, newest first, then the rest newest first; `mine` the asker's own light in full (its opaque `id`, so the page keeps it off the strings, the name, its years as `{ from, to }`, approved) when the session has one, else absent. The shared part is kept in the server's cache for five minutes (server:public-replies-cached) and `mine` is read fresh; a request with no session gets the shared part alone. The cached shared part is cleared whenever a light is lit, put out, approved or refused, so every other account sees a new light at once, and the reply is `private, no-store` so a browser never keeps a reply holding `mine`. `PUT /api/dedication/light` with `{ name, from?, to? }` is checked by content's `checkLight` and refused `bad-light` otherwise, the reply carrying the check's `problems` list; `bad-light` is a `ServerCode` (`packages/api/src/reply.ts`) and a rejection key of analytics:nightly-game-counters. One light per account: a second `PUT` replaces it and clears its approval; `DELETE /api/dedication/light` removes it. Both need a session (a guest's will do, account:social-needs-secured-account lists no bar) and count against the account limit (server:anonymous-limit-by-address); a `PUT` from a session with no account row is refused `signed-out`. The table `dedication_lights` (`account_id` primary and a foreign key that deletes with the account, `id` opaque, `name`, `from_year`, `to_year`, `lit_at`, `approved_at`, `approved_by`) is in the migrations (`0000_japacity`, server:migration-before-deploy); the table touches no life and needs no content version raise (`.claude/skills/japacity-shipped-lives`). The counts route of account:two-lights-and-wink-lines is `/api/lights`, apart from these.

## Contract

What the contract holds for this page:

1. `packages/sim`: `upgradeState(state: State, from: Content, to: Content) -> State`, pure, with a rename table on content: `Content.renames?: Record<string, string>` (old id to new).
2. `packages/sim`: `checkOverlay(base: Content, overlay: Overlay) -> string[]`, empty when the overlay may be applied (server:overlays-never-multiply-prices), beside `applyOverlay`.
3. `packages/sim`: `Save` is `{ schema; segments: SaveSegment[] }` with `SaveSegment = { content: string; overlay?: string; start: { scenario; seed; worldSeed } | { base: State }; commands: { command; tick; sender }[] }`, and `replay` runs the segments in order. A single-segment save loads as one segment. It bears on engine:state-is-plain-data (decision 0004).
4. `packages/sim`: the authority command list as data, `AUTHORITY_COMMANDS: readonly CommandType[]`, for the test in server:apologies-never-currency.
5. `packages/api` (`reply.ts`): `ServerRejection = { ok: false; code: ServerCode; detail: string; retryAfter?: number }` with `ServerCode` the engine's `RejectionCode` and the server's own codes: among them `rate-limited`, `signed-out`, `diverged`, `one-character`, `no-character` and `switched-off` (server:four-off-switches).
6. `packages/store`: `PlayerStore` with `transact(ids: string[], work: (rows) => Writes)` that locks in ascending id order; `CharacterRow = { id; account; v: number; refilledAt: number; segment: number }`; `LogRow = { character; v; tick; sender; command; hash; at }`; `SnapshotRow = { character; v; segment; content; overlay?; state }`.
7. `packages/store`: `LedgerStore` with `mark(character)`, `setMark(character, totals, day)`, `addDay(day, created, destroyed)`, `day(day)`.
8. `packages/store`: `AuditStore` for rows retired by server:rollback-apply-one-account and server:newer-content-upgrades-state.
9. Server config: `server = { snapshotEvery, seedBits }`, `limits = { commandsPer10s, commandsPer60s, readsPer60s, anonPer60s, socketPer10s, bodyBytes, adminBodyBytes, commandBytes, presetSteps }`.
10. `packages/store`: `SwitchStore` with `read(): Switches` and `set(name, on, admin, reason)`; `Switches = { signups: boolean; lottery: boolean; adverts: boolean; partnerPlay: boolean }`. Server config holds `switches = { cacheMs, retryMs }`.
11. Text key `server.full` (server:signups-off-shows-full).
